# Decisions made while porting the spec

The Python prototypes and reports under `swarm/`, `reports/` and `research_notes/` were the specification. Where they were silent, contradictory or needed data that is not on the build machine, these are the choices made. Each is easy to change; the file that holds it is named.

## Stack

- **Static site on Cloudflare Pages, no server.** HANDOFF.md planned a Cloudflare Worker proxying TMDB, and an intermediate plan a Vercel function; both were dropped. The site is the committed `site/` folder (no build step in the dashboard, `_headers` for the content security policy), and nothing in the page or the CLI makes a network request while an export is processed. The export never leaves the browser.
- **Text is outlined, not embedded.** The card draws every glyph as a path from Noto Sans/Serif JP Bold subsets, so there is no `<text>` and no font-loading problem. The cost is a larger SVG (about 650 KB) and a limited character set. Measured coverage of the subset (`tools/make_fonts.py` prints it): Basic Latin and the Latin-1 letters complete; Latin Extended-A 30 of 128 (Noto JP simply lacks the rest); Greek 48 of 56; Cyrillic basics 66 of 96; all hiragana and katakana; kanji only those on the card. Stand names are folded to plain capitals (`name::ascii_fold`: Dvořák becomes DVORAK, Søren Ærø SOREN AERO) and a composer with no ASCII form is skipped, so a name never has a hole in it; `tests/review_font.rs` checks every composer in the table, every Tarot name, every fixed label and every ability sentence, inside the 「」 brackets. Film titles and usernames from the export cannot be folded and draw □ for a missing character. `src/font.rs`, `tools/make_fonts.py`.
- **`gen_card.py` line 121 bug.** In embed mode the text lost the `f-` prefix on its class and rendered black. The Rust renderer has only the outlined mode and always emits `class="f-{cls}"`; a unit test fails if any bare class appears.
- **The film table ships with the page** (`site/films.json`) and the CLI embeds the same file. Films outside it are skipped by every stat that needs film data (Power, Precision, Range, Potential); Speed and Stamina read only the viewing timeline, so they count every watched film that gave a clean event; their coverage reads "224 of 533 dated watches" (bulk-import days excluded) so it is not mistaken for missing table data. Each stat reports "graded on N of M films" on the card and in `stand.json` (`coverage.per_stat`), and shows `?` when N is below the spec's minimum for that stat. The table carries its build date, and the CLI and page warn once it is older than six months, the longest TMDB's terms allow data to be cached.

## Deviations from the spec

Two choices contradict the written spec ("Letterboxd JoJo Stand stats 2"). Figures below come from `tools/evidence.py` run on the pooled Letterboxd users (sdl60660/letterboxd_recommendations) restricted to the films in the final table (9,787 films, built 2026-10-24).

### 1. Potential is graded on volume-matched Good-Turing (60 random films), against users with a similar number of films

- **Spec:** Potential = N1 / director credits over all of a user's films, with no cut-points; the volume-matched value was only an evidence line.
- **Now:** the card letter comes from the mean of 20 seeded draws of 60 director-credited films (N1 / credits per draw), graded within film-count bands (director-credited films: 60-100, 100-200, 200+). Each band has its own cut-points, cut on the pooled users in that band; a band with under 1,000 pooled users merges into its neighbour (none did). A user with 40 to 59 credited films is drawn on all their films, graded against the first band and marked provisional. The raw share stays in the card text ("47% directors seen once"), and the note names the band ("against users with 200+ films"). The 完成 symbol needs 1,000 credited films and the lowest band of the user's band, as in the spec.
- **Reason:** the raw share has a mechanical dependence on how many films were seen, so one set of cut-points cannot be applied fairly to a 60-film and a 500-film history. Drawing the same number of films per user removes the mechanical part, and banding by film count removes most of the remaining real dependence (users with long histories watch more varied directors).
- **Evidence.** Spearman correlation of the graded value with film count, over the pooled users restricted to the final table (33,643 users with at least 60 director-credited films):

| | Spearman with film count |
|---|---|
| raw Good-Turing, one population | −0.39 |
| volume-matched (60 films), one population | +0.34 |
| volume-matched, within the 60-100 band | -0.052 |
| volume-matched, within the 100-200 band | +0.104 |
| volume-matched, within the 200+ band | +0.183 |

  Per-band cut-points (10th, 30th, 70th, 90th percentile):

| Films | Pooled users | Spearman with film count | Cut-points |
|---|---|---|---|
| 60-100 | 3,038 | -0.052 | 0.610, 0.734, 0.886, 0.945 |
| 100-200 | 5,520 | +0.104 | 0.674, 0.758, 0.858, 0.916 |
| 200+ | 25,085 | +0.183 | 0.798, 0.854, 0.908, 0.934 |

- **Provisional rule.** Potential stays provisional while any band shows |Spearman| above 0.2. None does (largest 0.183, the 200+ band), so users with 60 or more credited films get an unmarked Potential grade. The 200+ band runs from 200 to a few thousand films and is the closest to the line, so a longer history could still drift upward within it; `tools/calibrate.py` prints the figures again whenever the table is rebuilt, and the rule is applied from them (`any_band_over_0_2` in `cuts.json`); `tools/refresh_table.sh` runs that calibration and `tools/build_tables.py` whenever the table is rebuilt.
- **Earlier result.** On the partial 920-film table the single-population volume-matched value looked flat against film count (−0.05); on the final table it is not (+0.34), which is why bands were added.
- **Cost:** a user is compared with others of a similar history length, not with everyone, so "C in the 200+ band" means middling among long histories. The canon-equivalent grade (used for the type and the nearest Stand) is cut within the band too, which can move a Stand match near a band's boundary: the author's Potential is 40.3rd percentile in the 200+ band, just under the canon boundary of 42.2, and the nearest Stand changed from D4C Love Train to Star Platinum (Part 6) at the same distance.

### 2. The crowd baseline is Letterboxd's displayed average, not the histogram plain mean

- **Spec:** the crowd is the plain mean from the rating histogram ("production uses the plain mean"), else the displayed average, else a bundled pool table, one source per grade.
- **Now:** every Power and Precision grade uses the displayed average (`lb_avg`), and the cut-points are calibrated on it.
- **Reason:** the collector reads a histogram for every one of the user's own films but, as the run was specified (`--hist-n 1000`), for only the first 1,000 sample films. Most table films therefore have a displayed average and no plain mean, and a cut-point is only valid for the crowd it was calibrated on. Mixing sources inside one grade is what the spec forbids; using the plain mean alone would leave most other users with no eligible films.
- **Evidence:**
  - Coverage: 997 of 9,787 table films (10%) have a histogram plain mean: only the first 1,000 sample films, chosen before anyone's list was read. The collector also read histograms for the author's own films, but the table drops those, because a plain mean on a film outside that first 1,000 would mark it as one of the author's; 9,782 (100%) have a displayed average.
  - Agreement on the 997 films that have both: displayed minus plain mean averages −0.008 stars, RMSE 0.086, largest difference 0.51 (the spec measured RMSE 0.056 on 15 films).
  - The cut-points moved with the baseline, as the spec expected: pooled users' mean offset to the displayed average is −0.045 stars, so the Power cuts sit higher than the spec's pool-scale ones (grade B starts at +0.20 instead of +0.14).
- **Cost:** the displayed average is Letterboxd's weighted score, which discounts unusual rating patterns, so it is slightly less exact than the plain mean. The histograms stay in the film table so the baseline can be switched back once they cover most of it (`crowd` in `stats.rs`, then recalibrate with `tools/calibrate.py --source hist`).

## Calibration (what the card letters rest on)

- **Power, Precision, Range, Potential** are cut on the pooled Letterboxd users restricted to the films in our table (`tools/calibrate.py`, joined by film slug, output `tools/calibration.json`, merged by `tools/build_tables.py`). Power: shrunk offset against the displayed average, users with at least 50 eligible films. Precision: the difficulty curve h(gap) and the population accuracy are refitted on the same users. Range: 20 draws of 50 films with fractional countries (the spec's procedure; users with at least 50 films). Potential: see deviation 1.
- **Final cut-points** (10th, 30th, 70th and 90th percentile of the pooled users): Power -0.367, -0.115, 0.199, 0.458 (34,523 users); Precision 0.654, 0.722, 0.796, 0.840; Range 2.14, 2.63, 3.73, 5.02 (34,720 users, median 3.10); Potential per film-count band, see deviation 1 (33,643 users). The Range cuts moved up sharply from the US-heavy proxy the spec used (median 2.47, cuts 1.9 to 3.3) once every pooled user's films have country data. Dropping the three ambiguous films and the author's own films from the table left the cuts essentially unchanged (Range 2.142, 2.625, 3.735, 5.019 before).
- **Table coverage** (`tools/coverage.py`, pooled users, TV removed). Share of a user's rated films found in the table: median 95.9%, 10th percentile 80.8% (users with at least 50 ratings; 35,718 users). Share also usable for Power and Precision (at least 30,000 Letterboxd ratings): median 93.2%, 10th percentile 72.7%. 1.2% of users would see `?` for Power and Precision because more than half of their rated films are missing. These figures are favourable by construction, since the table is the pool's own most-rated films; an independent check is the author's export, where 89.9% of watched films are in the shared list (the author's own films are no longer part of the shipped table). A user with obscure taste will see lower coverage, and the card says how much.
- **Coverage caveat.** Pool users contribute only the films that are in our table, which are popular films, and the product likewise uses only table films for Range and Potential, so the two are on the same footing. A user whose taste is mostly outside the table is graded on fewer films, and that is shown on the card.
- **Percentiles** (used by the ability engine to pick the most extreme stat) interpolate the probit of 13 population quantiles (1st to 99th) against the value and extend the end segments linearly.
- **Speed and Stamina** cuts are recomputed from `mt_user_metrics_N8.csv` (users with at least 20 clean events and 12 months); the four spec cut-points are reproduced exactly. They stay provisional until real dated Letterboxd exports exist.
- **Symbols:** ∞ for Speed needs pace ≥ 26.2 with 24 months and 40 events; for Stamina, 60 months all active; for Range, the 99.9th percentile of the calibration users with at least 50 films (the cut is computed over all of them) and the user must have at least 150 films with countries. 完成: see deviation 1.
- **"Crowd missing for more than half the rated films" gives `?`** for Power and Precision. A film needs at least 30,000 Letterboxd ratings to count.

- **Title and year collisions.** The table is joined to an export by normalised "title|year" (the cached Letterboxd pages hold no `boxd.it` short links, so a code match is not available without refetching every page). Two different films that share a key cannot be told apart, so every row of such a key is dropped and logged in `tools/table_collisions.json` (Cobweb 2023, Leo 2023, Reality 2014): those films are skipped for every user instead of one film's data being given to another. Keys are also compared against the author's own films, so a collision with one of them removes the row too. The Rust and Python key functions can differ for scripts whose vowel signs are combining marks (Devanagari); none of the shipped titles is affected.
- **File names.** The export date and username are read from the timestamp in the file name wherever it sits, so "(1).zip", " - Copy" and a query string change nothing.
- **Unreadable cells.** A date with a non-ASCII character is ignored; a rating that is not a number from 0.5 to 5 (NaN, inf, 9) is ignored and counted, with a note in `stand.json`. The engine returns errors instead of panicking on these.
- **Composer names for unrated users.** Users with ratings rank composers on two or more rated films by the shrunk mean of their ratings; users without ratings rank by how often a composer appears among the watched films (ties: the higher Letterboxd average of those films, then the lower id). Tarot names only when no composer credit is usable.

## Behaviour the spec left open

- **Join day** comes from the `Date Joined` column of `profile.csv`; only when the file or that column is missing (or the value is unreadable) is it the earliest `watched.csv` date, and `stand.json` says so in `notes`. **Export date** comes from the ZIP file name, else the latest date in the export.
- **Type ∅ or ?** on a stat a rule reads skips that rule. A user with all-∅ stats (an empty export) matches the canon Stand whose cells are all ∅ (Gold Experience Requiem).
- **Matching** with unknown user stats rescales by 6/k and needs 4 known stats. Ties between Stands at equal letter distance are broken in the spec's order: smaller salience-weighted error, smaller largest single gap, more exact grade matches, more known canon cells. The spec's last rule, canon order, is replaced by two: the continuous distance between the user's percentiles and the midpoint of each Stand's canon-equivalent percentile band (from canon's cumulative grade shares; ∅ at the bottom, ∞ at the top, 完成 in the lowest band; only stats where both have a value), then a hash of the username and the Stand name, which also splits identical-chart twins. The top 3 are distinct charts. For the author's profile (canon-equivalent B A C A A D), D4C Love Train and Star Platinum (Part 6) are equal on every earlier key (distance 1.4142, salience 2.0, largest gap 1, 4 exact matches, 6 known cells), so canon order (wiki row 97 against 124) had put Star Platinum (Part 6) first; the continuous distance now puts D4C Love Train first (Potential at the 40th percentile is 0.16 from the C band's midpoint and 0.26 from the lowest band's).
- **Matching reachability and concentration** (`tools/reachability.py`, `tools/reachability.json`; all 15,625 letter profiles weighted by canon grade shares, Method H, identical-chart twins sharing the mass). The spec's figures reproduce exactly with canon order: 141 Stands reachable, top-1 2.40%, top-10 19.2%, Gini 0.439, 93.2 effective Stands. With the continuous-distance and hash rule: **143 reachable**, top-1 2.50%, top-10 18.7%, Gini 0.430, 94.7 effective Stands (the user's percentile taken at the midpoint of their own band; drawing it uniformly inside the band gives 143 reachable, top-10 18.6%). Notorious B.I.G and Made in Heaven became reachable; no Stand lost reachability. Ten Stands remain unreachable (Atom Heart Father, Super Fly, Gold Experience Requiem, Rolling Stones, Jail House Lock, Bohemian Rhapsody, Burning Down the House, Dragon's Dream, Civil War, California King Bed). The spec explains six of them (Atom Heart Father, Super Fly, Bohemian Rhapsody, Burning Down the House, Dragon's Dream, Civil War) as needing Range ∅ or ∞, which the letter grid cannot produce; the other four (Gold Experience Requiem, Rolling Stones, Jail House Lock, California King Bed) were unreachable under canon order as well.
- **Example film per stat** (the second line of each card cell): Power, the film furthest from the crowd in your direction; Speed, your highest-rated film of the busiest month; Range, your highest-rated film from your least common country; Stamina, your highest-rated film of the last month of your longest streak; Precision, the most-rated film you scored within 0.25 of the crowd; Potential, your highest-rated film by a director you saw only once.
- **Range draws** use a fixed SplitMix64 stream (seed 5), 20 draws of 50 films, so results are reproducible in Rust, Python and across platforms. Fewer than 50 films with countries gives `?`.
- **Shorts** (runtime of 40 minutes or less) are ignored for countries, directors and composers; TV entries are dropped by the table builder.
- **Names (accepted for v1).** *Superseded by Agreed v1 design (25 Oct), below.* Only two kinds of name exist offline: a composer name (the composer with the highest shrunk mean over at least two rated films, else the most frequent composer among watched films, so unrated users still get one; names that cannot be drawn in ASCII or that collide with a canon Stand are skipped) and, only when no composer is usable, the Part 3 colour plus Tarot card. The music-title route (stages 4 to 8) needs tracklists from MusicBrainz or Discogs, which cannot be shipped and are not fetched. No katakana reading is produced.
- **Unclassified** is written 未分類 on the card (the spec names the type but gives no Japanese label).

## Agreed v1 design (25 Oct)

The naming route follows `docs/naming-spec.md` (nine stages); these agreed changes override that spec where they conflict. The spec's own section "Changes agreed on 25 Oct 2026" holds the same five points.

- **Soundtrack data is the local MusicBrainz dump** (`~/lb_collect_out/mb_local.jsonl`, built by `tools/mbdump/`), not the stage 4 cascade of API lookups.
- **Pool.** A(f) = 0.40 favourite + 0.25 own rating percentile + 0.15 own-minus-crowd percentile + 0.10 rewatch percentile + 0.10 composer affinity. The pool is the top 8 films that have candidates.
- **Names must be evocative.** Cool(n) in [0,1] combines word rarity, phrase shape, concreteness or emotion ratings, a lone-proper-name penalty and a canon word-count prior. It is tuned on the canon album benchmark (`tools/naming/data/canon_albums.json`: 38 of the 41 canon Stands named after a song resolve to an album and tracklist; 3 are listed as unresolved, not guessed).
- **Score.** S = 0.45 Cool + 0.35 F + 0.20 A, with a lexicon-only F. A candidate below the pool's median Cool cannot win. Among scores within 0.03 of the top, a hash of the username picks.
- **The Stand assigns its own name.** No user choice is required.
- **Glasgow Norms** (Scott et al. 2019, Behavior Research Methods 51:1258) supply the concreteness and emotion ratings. The article is CC BY 4.0 (Crossref licence record, Europe PMC `cc by`); the csv supplement carries no licence text of its own, so it is taken to fall under the article's. Attribution is required wherever the ratings are redistributed. The tools read them from `$NAMING_DATA` and ship nothing from them.

- **Cool ships as a documented heuristic, not a benchmarked ranker (25 Oct).** The canon album benchmark (`tools/naming/benchmark.py`) keeps 31 of 38 resolved Stands after the rule-based exclusions (more than 30 tracks, or a live / tour / session release): 9 for training (Parts 4 and 5), 15 for testing (Parts 6 to 8). At n=15 it cannot separate Cool from the first-track rule (paired MRR difference -0.12, 95% CI -0.37 to +0.12, for the best train-tuned weights). The stop condition in the task ("tuned Cool must beat first-track outside its interval") was miscalibrated for this sample size. Human review of the top-5 lists is the acceptance gate.
- **Cool weights.** Equal weights over the six features: each is scaled to [0,1], the lone-proper-name penalty is negative, and raw Cool is min-max scaled to [0,1] over the candidates table. The train-tuned set (concreteness alone) is not used: it comes from 9 Stands. No weight set has support in the data, so equal weights are the uninformed default. The equal-weight test-split row is kept in the benchmark output for the record and is not a gate.
- **Shipped candidates are track titles only.** Composer names are not in the candidate data; the composer route is the first fallback after the pool.

- **Candidate payload: 600 KiB gzipped, a separate file, cuts kept.** The 0.4 MB target was never measured; the first measurement showed that even the two ordered cuts (Cool below the global 40th percentile, then the top 6 candidates per film by Cool + max L) leave 522 KiB. Cutting more content would weaken F, so the budget was raised to 600 KiB instead. The data ships as `names.json` (28,235 candidates for 5,065 films, track titles and artist credits only, no MusicBrainz tags, genres, ratings or annotations); `films.json` keeps its format. The page fetches both files at load, in parallel, before the drop zone is active, and makes no request after a file is dropped.

- **How the pool is computed (`crates/standuser-core/src/pool.rs`).** The user's films are the watched or rated films the film table knows. Each q is a mid-rank percentile over the films that have that value and is 0.5 for a film without one: own rating, own minus Letterboxd average, rewatch count (diary rows whose Rewatch column says Yes; 0 for the rest), and the film's best shrunk composer mean (sum + 3 mu) / (n + 3) over the composers the user has rated at least one film of. Favourites are the `boxd.it` codes of the profile's Favorite Films cell matched to the codes in ratings.csv and watched.csv. Films with equal A (every film, for a user with no ratings, favourites or rewatches) are ordered by Letterboxd average, higher first and a film without one last, then by lower TMDB id (spec stage 3 order; its favourite and gap keys are already inside A). S is rounded to 4 decimals; ties inside the 0.03 band are listed by S, then name, then TMDB id before the FNV-1a hash of the lower-cased username picks. The first-track comparison is the lowest-numbered surviving track of the pool's highest-affinity film.
- **Why line.** One sentence from the spec's stage 8 template: how the name was cut from the title, the track, album artist, film and year, whether the film is a favourite (with the user's rating), then one cited reason (changed 26 Oct, see "Cited reason" below). The line is rendered from templates with `{slot}` placeholders; a check rejects any rendering with a number or capitalised word that is neither a template word nor in a slot value, and falls back to the bare facts. The card shows it in two 14 px lines under the name; `stand.json` carries it too. "Various Artists" albums are written without the artist.
- **Lexicon sources.** The core lexicons use the crate's template text first, then the wiki phrases the research note quotes for each canon Stand; templates 1, 4, 10, 12, 14 and 17 still needed a WordNet-definition top-up to reach 10 words, and `docs/naming-lexicons.md` labels those rows.

- **Ring cleanup (25 Oct), two rules for all 17 templates, no exceptions per template or name.** Generic motion verbs (go, travel) gave F = 0.5 to unrelated titles through the WordNet ring (for Wind Reading, TRAVEL SOUTH, GOING HOME and WORM RIDE all scored F = 0.5 on "float", "move" and "wind" links). (a) A ring link made only through a core word added by the WordNet-definition top-up is dropped: a top-up word is a definition word of a core word, not a word of the ability text, and its neighbours drifted furthest. (b) For every remaining ring lemma, the frequency is the share of the shipped candidates that contain it; the (template, lemma) pairs of all templates form one distribution and the pairs above its 90th percentile (nearest rank, share 0.00103) are dropped. The drop list is `tools/naming/data/ring_drop.json` (made by `tools/naming/clean_rings.py`; first on the names file as shipped before the change, now on the candidates table, see "Ring cleanup counts from the candidates table"). Effect: rings shrank from 3,990 pairs after (a) by 381 more; of the shipped candidates, those with any F match fell from 21,363 to 11,857 of 28,235, and among the 22,932 candidates shipped both before and after, 5,675 lost every match. Wind Reading keeps "weather" and loses "travel" and "go" (rule b) and "ride" and "fall" (rule a). Cut 2 ranks by Cool + max L, so 5,303 candidates swapped places in the shipped set; the file is 479 KiB gzipped.

- **Sensitive-phrase blocklist (25 Oct).** A Stand's name appears on a person's profile, so stage 6 rejects names that are real-world discrimination, atrocity or violence against people (a seeded synthetic user won RACIAL PROFILING, a track on the Source Code soundtrack). The list is `tools/naming/data/sensitive_phrases.txt` (about 40 phrases: racial profiling, hate crime, genocide, massacre, suicide, gas chamber, slavery and the like), matched as whole phrases after folding and dropping punctuation, so "Slave to the Rhythm" and "Racial Harmony" pass. It is one list for every film and user, read by the builder and by the Rust tests; it rejected 96 track candidates (92 rows left the candidates table), 46 shipped candidates were replaced by 38 others, and `names.json` is 476 KiB gzipped. A blocklist catches phrases, not meaning: the acceptance gate for names stays the human review of the top-5 lists.

- **Names file format 2: the artist and the score flag belong to the album (26 Oct review).** A film can have candidates from a score, a songs album and a various-artists album, and format 1 stored one artist and one flag per film (the first album's artist, the last row's flag), so a track could be credited to another album's artist or called a score or soundtrack wrongly: on 12 Years a Slave both LETTER WRITING (Zimmer's score) and FREIGHT TRAIN (the songs album) read "Hans Zimmer's 12 Years a Slave soundtrack". `names.json` v2 holds, per TMDB id, `[[[artist, flag], ...albums], [[name, cool, track, kind, src, codes, album], ...]]`; each candidate's last element indexes its film's albums, and the why line takes the artist and score / soundtrack word from that album. The loader refuses any other `v`. In the candidates table 462 films have candidates from two or three albums; after the cuts 398 shipped films do, and 2,768 shipped candidates (466 films) now carry a different artist or flag than before. The candidate set itself did not change (28,202 candidates, 5,065 films).

- **A function word never ends a tail (26 Oct review).** `textlib.is_noun` treated a word WordNet does not know as a proper noun, and WordNet does not know "the" (nor "of"), so the stage 5 tail rule accepted tails such as "Run for the"; some function words are WordNet nouns (will, may, mine, one, us, me). `is_noun` now returns False for every word in `FUNCTION_WORDS`. The candidates table lost 571 tail rows (3,283 to 2,712, none added; e.g. WANT ME, LOVE YOU, USED TO BE, PLACE TO BE); in the shipped file 324 of the 1,446 tails left the top 6 of their film, 17 tails came in, and the file now holds 28,148 candidates for 5,064 films. A real noun that is also a function word ("Last Will") no longer ends a tail, as the rule asks.

- **Ring cleanup counts from the candidates table (26 Oct review).** `clean_rings.py` took the lemma frequencies from the shipped `names.json`, which the drop list itself shapes (the file is built with the list, and its top-6 cut ranks by max L), so each run on the file it had just helped build gave a different list. It now counts the candidate rows of `local/naming/candidates.csv` (91,087 rows, composer-name rows left out) and the core lexicons only; it has no `--names` option. Two runs, and a run after rebuilding `names.json`, write the same `ring_drop.json` (sha256 d0ba1791). The 90th-percentile share is now 0.00052 over those rows (0.00103 over the 28,235 shipped candidates before), rule (b) drops 396 pairs (381 before), and Wind Reading still loses go and travel. Effect on the shipped file: 861 of 28,148 candidates changed (the top-6 cut re-ranks by max L); of those shipped both times, 303 lost every match and 298 gained one; candidates with any F match 11,725 to 11,372; 480 KiB gzipped.

- **Cited reason (26 Oct review).** Spec stage 8 asked for "the cited reason is the largest term in S" (fit, Cool or affinity, each with a rank). That rule is replaced: when F > 0 the line cites the matched word, `"<word>" fits your <ability> ability` (a ring word, F = 0.5, reads `is close to` instead of `fits`); when F = 0 it cites the film's link to the user, `<film> is one of your Favourite Films` for a favourite and `<film> ranks <i> of <N> films in your pool by affinity` otherwise, each followed by the user's rating when there is one. Cool is never cited (it still weighs 0.45 in S). The fit rank and the "highest-affinity films" wording are gone. The check that the cited reason is the largest term of S is gone with the rule. The line is built from named templates (`T_HEAD`, `T_PLACE_ARTIST`, `T_LINK_FAV`, `T_FIT_CORE`, ...) filled from slots; the artist enters as one slot already in its possessive form (`The B-52's`, `Pixies'`, `Hans Zimmer's`), because the old `{artist}'s` produced `B-52's's`, a token no slot held, and the line fell back to the bare facts. The template words the check allows are Why, Favourite and Films.

- **`stand.json` no longer carries `coverage.favorites_read` (26 Oct review).** The count of favourite films read from `profile.csv` was only a debugging figure; the file keeps the per-film favourite flag (`fav` on each listed name's film), which is what the why line and the report use.

## Privacy

- `profile.csv` is read through an allowlist of two columns, `Date Joined` and `Favorite Films`, in memory; from the favourites cell only the `boxd.it` film codes are kept. Every other column (the e-mail address and the username included) is never decoded, stored, shown or logged, a test puts invalid UTF-8 in the e-mail column to prove it is not decoded, and an unreadable `profile.csv` counts as absent. The username comes from the ZIP file name (or `--username`). The committed fixtures use a synthetic `profile.csv` with an invalid address.
- The real export was run without `profile.csv`; the join day was passed as `--joined 2022-07-06` (from the spec) and the username came from the file name.
- The shipped film table is the shared film list only: no Letterboxd codes, and none of the author's own films (the earlier table carried the codes of the author's 514 watched films and thereby listed them). The real-export fixtures (a table that includes the author's films, and the golden file with their activity dates) live in the gitignored `local/` folder; the committed fixtures are synthetic. The git history still contains the earlier fixtures and was not rewritten.
- The export never leaves the browser, and the page makes no request after it has loaded: no proxy, no analytics, no fonts or images from other sites. A browser test asserts zero requests while an export is processed. The only outbound thing on the page is the TMDB logo link, which the visitor has to click.


## Testing

- `cargo test --workspace` runs the unit tests, the CLI tests, the edge cases, the golden test against the synthetic export, and the regression tests from the independent review (`crates/standuser-core/tests/review_*.rs`, one file per finding).
- **What the golden tests prove.** `tools/golden/ref.py` re-implements most of the pipeline in Python next to the prototypes it copies, so the golden comparison catches the Rust drifting from the Python; it cannot catch a misreading of the spec that both share. Every spec mismatch the review found (Range provisional, unrated composers, the card labels) passed the golden tests, which is why each now has its own test written from the spec's wording.
- **The real-export test** is `#[ignore]`d: a normal run reports it as ignored and it fails if its three environment variables are missing, so it can never pass silently. CI regenerates the synthetic golden file and diffs it against the committed one (`tools/golden/compare.py`).
- `tools/site_test/run.sh` drives the real page in headless Chrome and asserts zero network requests while an export is processed.
